# #107 SDD：背景工作重啟續跑不重複建候選（Dev-B）

依據：spec 6.1（例外表「服務重啟時有 `running` 工作」）、FR-INB-08（續跑最多 2 次）、AC-41；todo 7.5；#107（Dev-A 13.5 演練發現）。
狀態：**已定案（Q1＝B），實作中**（2026-11-20）。

## 0. 現況與問題

`worker.run_once` 處理一筆工作會用到三種交易，彼此獨立：

| 順序 | 位置 | 交易內容 |
| --- | --- | --- |
| 1 | `jobs_repo.claim_next` | 工作 `queued → running` |
| 2 | `process_sources` 迴圈每次嘗試 | `jobs.attempts = n` |
| 3 | `_save_candidates`（成功那次） | `ai_runs(status=ok)`＋全部 `candidates` |
| 4 | 回到 `run_once` | 工作 `running → succeeded／failed`＋`result` |

行程在 3 與 4 之間崩潰時，工作停在 `running`；重啟後 `reset_running` 把它改回 `queued`，`process_sources` 從頭再跑一次。會出現兩個症狀：

- **症狀 1（#107 已寫）**：再呼叫一次 AI-01、再存一份候選，收件匣出現兩筆相同的候選，也多花一次 AI 費用。
- **症狀 2（#107 沒寫，讀程式碼推得）**：如果崩潰前那次成功的是**第 3 次嘗試**，重跑時 `attempts_done=3`，`while attempt < MAX_ATTEMPTS` 一圈都不會跑，直接回傳 `unavailable`。結果工作被標成 `failed`，訊息是「AI 解析失敗」，**但候選其實已經存在收件匣裡**。

**已有的保證**：第 3 步把 `ai_runs(ok)` 和候選放在同一個交易裡，所以「這個工作有一筆 `status='ok'` 的 `ai_runs`」⇔「這次的候選都已經存好了」。兩個改法都建立在這一點上。

## 1. 討論決議

- **D-1（2026-11-20 Mora）採用 B：續跑前查這個工作有沒有 `status='ok'` 的 `ai_runs`**。
  架構後果：(a) 只改 `process_sources` 開頭與兩個 repo 查詢；`worker.py`、同步收件路徑不動 (b) 正確性依賴「`ai_runs(ok)` 與候選同一交易」，由 T1 固定 (c) 崩潰到重啟之間，候選可能先於工作結案出現，重啟後自動補成 `succeeded` (d) Q2 照預設：查到 ok 時 `attempts` 不加一。

## 2. 待釐清問題

### Q1 改法：A（同一個交易）還是 B（續跑前查 ok 的 `ai_runs`）？

| | A：存候選＋結案放在同一個交易 | B：續跑前先查這個工作有沒有 ok 的 `ai_runs` |
| --- | --- | --- |
| 做法 | `process_sources` 改成回傳草稿或接收一個結案回呼，在第 3 步的交易裡一起把工作改成 `succeeded` 並寫 `result` | `process_sources` 開頭，`job_id` 不為空時查 `ai_runs WHERE job_id=? AND status='ok'`；查到就讀出該 run 的候選 id，直接回傳 `Outcome("ok", …)`，不呼叫 AI；`run_once` 照原本的流程結案 |
| 症狀 1 | 解決：第 3、4 步合成一步，不再有中間狀態 | 解決：重跑時查到 ok，不再呼叫 AI 或建候選 |
| 症狀 2 | 解決 | 解決（檢查放在嘗試次數迴圈之前） |
| 改動範圍 | `ingest.py`（`process_sources`、`_save_candidates`）、`worker.py`；**同步路徑（≤ 30 行）也走 `process_sources`，要一起改**；`result_summary` 需要 payload 裡的 `duplicates`、`unparsed_lines`，得傳進交易 | `ingest.py` 加約 5 行；`ai_runs_repo`、`candidates_repo` 各加一個查詢函式；`worker.py` 與同步路徑不動 |
| 崩潰到重啟之間 | 不會出現「候選已在收件匣，工作還是 `running`」 | 會出現（重啟後自動補成 `succeeded`）。前端輪詢超過 60 秒本來就會停，顯示「稍後回收件匣查看」，使用者看得到候選 |
| 職責 | `process_sources` 要知道「工作」，同時負責 AI 與工作結案 | 工作結案仍只在 `run_once`；`process_sources` 只多了「已經做過就不重做」，可以重複執行（冪等） |
| 風險 | 改到 AC-40、AC-41 與同步收件測試涵蓋的共用路徑 | 依賴第 0 節的保證；之後有人把 `ai_runs(ok)` 和候選拆到兩個交易，B 就失效，所以要用測試把這個前提固定下來 |

**建議：B。** 理由：
1. 判斷依據是資料庫裡已經保證一致的狀態（ok run ⇔ 候選），不是靠時序或旗標，屬於「從結構取真相」。
2. 改動只在背景工作這條路徑；同步收件與 AC-40／41 的路徑不動，回歸風險最小。
3. 開發原則第 5 條「最簡單、符合既有結構」：工作結案仍集中在 `run_once`，不必把工作概念帶進 `_save_candidates`。

A 的唯一實質優點，是崩潰到重啟之間不會有短暫不一致。但這段期間服務本來就停著，使用者也只會看到候選比工作狀態先出現，不會出錯。

### Q2（不需裁定，照預設做）續跑時 `attempts` 要不要加一？

預設**不加**：查到 ok 時沒有呼叫 AI，也就不算一次嘗試；spec 6.1 只要求「嘗試次數保留」。`result` 由 `run_once` 依查回的候選重新組出，`created`、`skipped` 的算法與第一次相同（`skipped = 來源數 − 候選數`）。

## 3. 實作與測試計畫（以 B 為例；裁定 A 時改寫本節）

先寫紅燈測試（`tests/unit/test_phase7_inbox.py`，沿用 `ingest`、`long_text`、`NODE` 等輔助函式；只用 `FakeAIClient`）：

| 測試 | 情境 | 預期 |
| --- | --- | --- |
| T1（#107 重現） | 第 1 次嘗試成功；`jobs_repo.update` 寫最終狀態時丟例外 → `reset_running` → `run_once` | 候選仍是 1 筆；這個工作的 `ai_runs` 只有 1 筆（AI 只呼叫一次）；工作 `succeeded`，`result.candidate_ids` 等於第一次存下的 id |
| T2（症狀 2） | 前兩次 AI 不合格式、第 3 次成功；同樣在結案時崩潰 → 重啟 → 重跑 | 工作 `succeeded`（不是 `failed`），候選不重複 |
| T3（反向） | 崩潰時只有失敗的 `ai_runs`（沒有 ok） | 重跑照常呼叫 AI 並建立候選（確認 B 只認 `status='ok'`） |

然後實作：
1. `ai_runs_repo.ok_run_id_for_job(conn, job_id) -> int | None`，`candidates_repo.ids_for_run(conn, run_id) -> list[int]`（參數化查詢）。
2. `process_sources`：在私人專案檢查之後、組 payload 之前，`job_id` 不為空時經 `_saved_candidate_ids` 呼叫上面兩個函式；查到就 `return Outcome("ok", attempts_done, ids, skipped=len(source_ids) - len(ids))`，並留一行 `log.info`（只記 job id 與筆數）。
3. 模組 docstring 補一句：重跑時以 ok 的 `ai_runs` 判斷已完成。

驗收：T1～T3 先紅後綠；後端全套 pytest 綠；ruff 綠。不改 DDL、API、`AIClient` 契約。完成後在 #107 留言附 PR，由 Dev-B 關閉 issue；在 #108 或 deploy.md 第 10 節的「已知問題」由 Dev-A 決定要不要改寫成「已修正（#107）」，開 PR 時 @ 知會。
