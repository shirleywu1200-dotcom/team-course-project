## 3. 自動測試設計

- 檔案：`backend/tests/acceptance/test_ai_outage.py`（新增，只加測試，不改程式）。
- 一個 SQL 種子：一個工作專案、幾個任務（含一個已完成且有回報的）、一個目標、一週事件。
- AI 用 `FakeAIClient(available=False)`，不寫任何 script。
- **AI 端點**：上表範圍內的每個端點各一個斷言，檢查狀態碼、`ai_status`，以及退路內容存在。各端點的細節已有專屬測試，這裡不重複，只確認「AI 全關」時每個端點都走到退路。
- **非 AI 主流程**：同一個 app 依序跑建專案、建任務、改期（`adjust-due`）、完成、完成回報、關聯目標，每步都斷言 2xx。
- **不寫 `ai_runs` 的情況**：只斷言 spec 有寫的。AI-01 不可用時記 1 筆後就停；私人範圍不送的情況不在這裡驗，已有專屬測試。

已有專屬測試的端點仍放進掃描，目的是用一支測試回答「AI 全關時有哪些端點」。之後新增 AI 節點（AI-02、AI-04）時，加在這支測試裡。

## 4. 手動演練

1. 用 `scripts/e2e_server.py` 起暫時資料庫 `g4_e2e`，環境變數設 `AI_PROVIDER=anthropic`、`ANTHROPIC_API_KEY=<明顯無效的假字串>`。`config.py` 用 `setdefault` 讀 `local.env`，行程環境變數優先，所以真 key 不會被讀到。啟動前先印出 key 長度與前 3 碼，確認是假值才繼續（不印整個 key）。
2. 依第 2 節的表格逐一打端點，記錄狀態碼、`ai_status`、`ai_runs` 的 `status` 與 `error`。
3. 另跑一輪 `AI_PROVIDER=off`，作為對照組。
4. 在前端走一遍收件匣、匯入、週報、目標頁，確認畫面有退路提示，沒有紅框或卡在載入中。
5. 結果貼到認領 issue；走查完用 `--drop` 刪庫。

不會產生費用：無效 key 會在供應商端回 401，不計 token。
