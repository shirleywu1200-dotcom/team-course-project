## 2. 資料流

```
GET /projects ─→ TargetPicker（新建名稱／既有專案；私人專案標「不會送 AI」）
                    │ target 或原文改變 → 清掉預覽與「對應已確認」
POST /projects/import/preview { text, target, new_name, column_map? }
   └→ preview 結果（單一 useMutation 狀態，不另存副本）
        ├ mapped_by=null → 只顯示 MappingPanel，指定 title、end 後帶 column_map 重送
        ├ mapped_by=ai   → MappingPanel 顯示「確認對應」；改任一欄 → 帶 column_map 重送（回 manual）
        └ rows → DiagnoseTable（唯讀，blocking 列可勾略過）
POST /projects/import/commit { target, new_name, rows[+skip], ai_run_id?, column_map? }
```

- **單一事實來源**：列與診斷只來自最近一次 preview 回應；前端只自管三個狀態：`skip` 集合、`confirmed` 旗標、第一次拿到的 `ai_run_id`。
- **保存鈕可按的條件**（純函式 `canCommit`，單獨測試）：有 preview 列；`mapped_by` 為 `ai` 時 `confirmed`；每個 `blocking` 列都在 `skip` 裡；可匯入列 ≥ 1。後端仍會重新驗證（AC-31），前端條件只是避免白送。
- **冪等**：commit 帶 `Idempotency-Key`（沿用 `newIdempotencyKey`），送出期間停用按鈕。
- **實作順序**：後端 `CommitIn` 是 Strict 模型，多帶欄位會 422；所以前端第一版不送 `ai_run_id`、`column_map`，等 D-3 核可、後端改完再一起補（含下一點）。
- `ai_run_id` 保留規則（D-3）：第一次 preview 帶回才記；使用者改對應重送後回 `manual`、不再有 `ai_run_id`，前端仍沿用第一次的值送 commit，伺服器才比得出「changed」。改原文或改目標時清掉。

## 7. 測試（Vitest＋MSW）

- `canCommit`：未確認 AI 對應、blocking 未略過、可匯入 0 列各自擋下；全部滿足才可。
- `rule`：不顯示確認鈕，直接可保存；`ai`：確認前保存鈕停用；`null`：指定 `title`、`end` 前不顯示診斷，指定後帶 `column_map` 重送。
- 改對應重送後，commit 仍帶第一次的 `ai_run_id`；改原文或改目標後清掉 `ai_run_id`、`confirmed`、`skip`。
- 私人專案顯示「不會送 AI」；新建專案名稱空白時不能預覽。
- 413、commit 422（`VALIDATION_ERROR` 標列號、`EMPTY_SELECTION`）。
- 保存成功顯示建立數與略過數；commit body 的 `rows` 原樣帶 preview 的值與 `skip`。
