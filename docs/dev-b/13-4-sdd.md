## 1. 討論決議

- **D-1（2026-11-16）節點範圍與 prompt 位置 → 只接 Dev-B 的 AI-01、06、07，client 以節點登記表查找**。
  架構後果：(a) 每個節點一個檔案（prompt＋輸出 schema），放在 `backend/app/ai/nodes/`，client 依 `node_id` 查表 (b) 表內沒有的節點丟 `AIUnavailable`，Dev-C 的 AI-02～05 自動走 spec 6.6 退路，AC-50 不受影響 (c) Dev-C 之後新增自己的節點檔，不必改 client，不會和 Dev-B 衝突；格式定案後開 issue @ Dev-C 說明。
- **D-2（2026-11-16）供應商 → Anthropic Claude API，用官方 `anthropic` Python SDK；模型名稱由環境變數指定**。
  架構後果：(a) 結構化輸出直接用 D-1 各節點的 pydantic schema，由 API 約束 JSON 格式，client 解析失敗才丟 `AIInvalidOutput`（第 3 題大致隨之定案，驗證放在 client） (b) SDK 預設自動重試 2 次（408／409／429／5xx、連線錯誤，逾時也會重試），與呼叫端的重試疊加，見第 4 題 (c) API key 放 `env/local.env`，`example.env` 只加變數名 (d) 資料送往 Anthropic，spec「供應商資料處理條件」待決要在上線前確認。
- **D-3（2026-11-16）重試分層 → 關掉 SDK 重試（`max_retries=0`），只由呼叫端重試**。錯誤對應：逾時、429、5xx（含過載）、連線中斷 → `AITimeout`（呼叫端續跑）；401／403、400、未設定 key → `AIUnavailable`（直接走退路）；schema 解析失敗 → `AIInvalidOutput`。
  架構後果：(a) 單次請求最多 3 次呼叫，同步端點最久約 60 秒 (b) 每次實際呼叫都有一筆 `ai_runs`，FR-AI-02 的嘗試次數與延遲是準的 (c) 429／5xx 在 `ai_runs.status` 會記成逾時類；`ai_runs.error` 只放類別名稱（資安規則 3），要分辨原因時看 HTTP 狀態碼，只記數字不記回應內容。
- **D-4（2026-11-16）開關方式 → 環境變數 `AI_PROVIDER`，`off`（預設）或 `anthropic`**。
  架構後果：(a) 未設定時維持現狀 `FakeAIClient(available=False)`，CI、其他開發者與 QC 行為不變，不會意外產生費用 (b) 13.3 演練只要設回 `off`，或拿掉 key (c) 設成 `anthropic` 但沒有 key 時啟動不崩潰，每次呼叫丟 `AIUnavailable` 走退路（FR-AI-03） (d) 測試照舊用 `create_app(ai=FakeAIClient(...))` 注入，不讀這個變數。
- **D-5（2026-11-16）真實 AI 的驗證方式 → 手動觸發的冒煙測試＋標註集評估**。
  架構後果：(a) pytest 加 `real_ai` 標記，只有 `AI_PROVIDER=anthropic` 且有 key 時才跑，CI 自動跳過，key 不進 GitHub (b) `scripts/` 加評估腳本，用 QC-2 的標註測試集（約 30 則）跑 AI-01，輸出命中率、延遲、token 數，只印統計，不印原文（資安規則 3） (c) 每次執行都要花錢，要 Mora 同意才跑；評估結果作為 2b 選模型與 13.10 G2 校正的依據。

## 3. 預算控管（2a 衍生）

三層，由硬到軟：

1. **供應商端硬上限**（最可靠，不靠程式）：在 Anthropic Console 為本專案開一個獨立 workspace、建專用 key，並設該 workspace 的月花費上限；帳單用預付額度、關閉自動儲值。額度用完時 API 回錯誤，依 D-3 對應成 `AIUnavailable`，系統走退路，不會繼續扣款。
2. **評估腳本自我設限**：執行前先依輸入字數估算費用並印出，等確認才送；執行中累計實際 token，超過 `--max-cost` 就停止。
3. **事後對帳**：client 每次呼叫在 log 記 `input_tokens`、`output_tokens`（只記數字，符合資安規則 3），不改 `ai_runs` 結構；每週對照 Console 的用量頁。
