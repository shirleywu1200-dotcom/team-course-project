  架構後果：(a) 結構化輸出直接用 D-1 各節點的 pydantic schema，由 API 約束 JSON 格式，client 解析失敗才丟 `AIInvalidOutput`（第 3 題大致隨之定案，驗證放在 client） (b) SDK 預設自動重試 2 次（408／409／429／5xx、連線錯誤，逾時也會重試），與呼叫端的重試疊加，見第 4 題 (c) API key 放 `env/local.env`，`example.env` 只加變數名 (d) 資料送往 Anthropic，spec「供應商資料處理條件」待決要在上線前確認。
- **D-3（2026-11-16）重試分層 → 關掉 SDK 重試（`max_retries=0`），只由呼叫端重試**。錯誤對應：逾時、429、5xx（含過載）、連線中斷 → `AITimeout`（呼叫端續跑）；401／403、400、未設定 key → `AIUnavailable`（直接走退路）；schema 解析失敗、`max_tokens` 截斷 → `AIInvalidOutput`；拒答 → `AIUnavailable`（第 2 節第 10 題）。

- **D-4（2026-11-16）開關方式 → 環境變數 `AI_PROVIDER`，`off`（預設）或 `anthropic`**。
  架構後果：(a) 未設定時維持現狀 `FakeAIClient(available=False)`，CI、其他開發者與 QC 行為不變，不會意外產生費用 (b) 13.3 演練只要設回 `off`，或拿掉 key (c) 設成 `anthropic` 但沒有 key 時啟動不崩潰，每次呼叫丟 `AIUnavailable` 走退路（FR-AI-03） (d) 測試照舊用 `create_app(ai=FakeAIClient(...))` 注入，不讀這個變數。
- **D-5（2026-11-16）真實 AI 的驗證方式 → 手動觸發的冒煙測試＋標註集評估**。
  架構後果：(a) pytest 加 `real_ai` 標記，只有 `AI_PROVIDER=anthropic` 且有 key 時才跑，CI 自動跳過，key 不進 GitHub (b) `scripts/` 加評估腳本，用 QC-2 的標註測試集（約 30 則）跑 AI-01，輸出命中率、延遲、token 數，只印統計，不印原文（資安規則 3） (c) 每次執行都要花錢，要 Mora 同意才跑；評估結果作為 2b 選模型與 13.10 G2 校正的依據。
- **D-6（2026-11-17，#39 Dev-A 審查）SDK 內建 OpenTelemetry → 關閉：`anthropic.Anthropic(..., open_telemetry=False)`**。
  架構後果：(a) 程序內即使有全域 tracer provider，SDK 也不產生 span，提示與回應不會經 exporter 外流（資安規則 2）；明確傳入後 SDK 不再讀 `ANTHROPIC_OPEN_TELEMETRY*` 環境變數，部署環境設錯也打不開 (b) 單元測試在設了 `ANTHROPIC_OPEN_TELEMETRY_TRACES_CONTENT_MODE=content` 的環境下建立用戶端，斷言 traces 關閉 (c) trace context 傳遞（`propagation`）維持 SDK 預設：只在已有 span 時附 trace ID 標頭，不含內容。

## 4. 逾時校正（2026-11-20，已定案）

### 4.1 資料

- `ai_runs` 沒有真實資料：開發庫與 `g4_e2e` 平常都把 AI 關掉。真實延遲只能從評估 CSV（`../Dev-B工作紀錄/評估結果/`，11/16～11/20 共 13 份）取，全部是 effort low。

| AI-01 | Sonnet 5.5 | 36 | 1.8 秒 | 2.3 | 2.4 | 2.4 |
| AI-01 | Haiku 5.5 | 21 | 1.9 | 3.1 | 5.2 | 5.2 |
| AI-03 | Sonnet 5.5 | 30 | 2.5 | 5.6 | 6.2 | 9.5 |
| AI-04 | Sonnet 5.5 | 12 | 2.9 | 3.3 | 3.3 | 9.8 |

- AI-06、AI-07 沒有評估 CSV；13.4 冒煙時是 2～3 秒（本檔開頭）。
- 延遲主要跟輸出 token 數有關。Sonnet 88 筆線性擬合：**延遲 ≈ 1.6 秒＋每 1,000 輸出 token 約 5.2 秒**。樣本裡的輸出最多約 1,000 token，超過這個範圍的估計是外推〔假設〕。尾端有離群值：AI-04 只輸出 369 token 卻花了 9.8 秒，推測是供應商端排隊。

### 4.2 判讀

**同步節點（AI-03、05、06、07，以及 30 行以內的 AI-01）：20 秒維持不變。**
- 實測最大值 9.8 秒，約是逾時的一半；p95 在 6.2 秒以內。
- 呼叫端最多 3 次嘗試，同步端點最壞約 60 秒（D-3），這部分不變。
- 不改預設值，就不動凍結契約（`DEFAULT_TIMEOUT_S = 20.0`）。

**風險在 AI-01 的背景工作，不在 20 秒這個數字本身。**
- 超過 30 行會轉成背景工作，但 `process_sources` 是把**整份貼上內容用一次呼叫送出**，沒有分批；貼上上限是 `MAX_CHARS = 20_000` 字，換算約 600 行以上的聊天紀錄。
- 依 4.1 的擬合，20 秒大約只能容納 3,500 個輸出 token。AI-01 的 prompt 要求**每一則訊息都輸出一個 item**，閒聊也要輸出 `kind=none`，所以輸出量是跟著訊息數成長，不是跟著候選數。每則約 40～50 token，大約 70～80 則訊息就會碰到 20 秒〔外推〕；到了約 170 則訊息，會撞上 `max_tokens=8000` 被截斷（`AIInvalidOutput`）。
- 超過時，三次嘗試都會逾時，工作標成 `failed`。原文仍保留，使用者可以手動建任務（同 AC-40 的退路：失敗標 `failed`、摘錄保留）。功能不會壞，但大量貼上會直接失敗，而且每次失敗都要等滿 60 秒。
- `max_tokens=8000` 時，最壞約要 43 秒，本來就超過 20 秒。
