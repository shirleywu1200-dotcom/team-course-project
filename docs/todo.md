# 個人大總管 APP 開發待辦（todo.md）

依據：`spec.md` v0.1（含 AI-08 取消後的更新）。結構為兩層：**Phase → Task**。Phase 由基礎排到進階。

## 0. 使用方式與規則

### 0.1 低耦合規則（每個 Phase 都要遵守）

1. **只依賴下層的公開契約，不依賴下層的實作。** 契約只有三種：資料庫 DDL、API 錯誤格式、領域函式簽名（寫在各 Phase 的「對外契約」）。
2. **獨立測試用 SQL 種子資料，不用上游程式碼建資料。** 每個 Phase 的測試夾具（fixture）直接 INSERT 到 PostgreSQL 測試資料庫，所以上游壞了不會讓本 Phase 的測試失敗。
3. **AI 一律用 `FakeAIClient`。** 測試不連真實供應商；真實供應商只在 Phase 13 驗證。
4. **前端 Phase 只對 OpenAPI 契約測試**（以 MSW 模擬 API），不需要後端運行。
5. **每個 Phase 結束時主幹可部署、既有測試全綠。** 不留「下個 Phase 才會通」的半成品。
6. 所有任務標明對應的 `FR-*`、`AC-*`，以 spec 為準；發現 spec 衝突時改 spec，不在程式裡悄悄決定。
7. **人員配置：3 位開發（Dev-A／B／C）＋2 位 QC（QC-1／QC-2）。** 每個 Phase 有一位開發負責實作、一位 QC 負責驗收測試，分工見第 5 節。

### 0.2 狀態標記

`[ ]` 未做　`[~]` 進行中　`[x]` 完成　`⛔` 被待決事項擋住（見第 3 節）

Dev-A 註（2026-11-13）：Dev-A 範圍內標 `[~]` 的項目，表示已實作且 Dev 單元測試在 PostgreSQL 上通過，等 QC 驗收測試轉綠才改 `[x]`。進度與驗證方式見 `docs/dev-a-progress.md`。

## 5. 分工：3 位開發＋2 位 QC

假設：「3 個 PR」指 3 位開發（Dev-A／B／C），另有 2 位 QC（QC-1／QC-2）。產品負責人是你，負責裁定 spec 歧義與待決事項。本版**不做人天預估**；負載只用任務數與 AC 數大致平衡，實際速度待 W1 後觀察。開發方式為 vibe coding，作法見第 6 節。

### 5.1 角色與邊界

| 角色 | 做什麼 | 不做什麼 |
| --- | --- | --- |
| Dev | 實作、寫單元測試、維護本線的對外契約 | 不寫自己 Phase 的驗收測試；不自行解讀 spec 歧義 |
| QC | 依 spec 的 AC 寫驗收測試、維護 SQL 種子夾具庫、探索式測試、回歸 | 不讀實作程式碼來寫測試；不修正式程式碼 |
| 你（產品負責人） | 裁定 spec 歧義、待決事項、契約變更 | — |

**為什麼 QC 不看實作**：驗收測試的價值是獨立於實作。QC 只看 spec 與對外契約（DDL、OpenAPI、函式簽名），才能抓出「開發把規格理解錯但自己的測試也一起錯」的情況。這也是各 Phase 能獨立測試的實際保證。

2. **合併條件三項皆須成立**：開發自己的單元測試綠、QC 的 AC 驗收測試綠、另一位開發審查通過。

4. QC 發現缺陷分兩種：**程式缺陷**（回開發）；**規格歧義**（回你裁定，開發與 QC 都不自行決定）。
5. 防回歸測試（FR-AI-06）：3.5、7.9、9.4、12.2 四個測試，由 QC 持有，任何人不得刪除或放寬。
6. QC 領先規則被破壞（驗收測試還沒寫就開始實作）時，該 Phase 不算開工。

### 5.9 風險與取捨

- **Dev-A 是關鍵路徑**。他慢，Phase 3、4 與 B 的 Phase 7 都等；所以 W1 刻意把第一片切小，只含 DDL、觸發器、`write_event`、樂觀鎖。
- **Dev-B 在 W1 只做純函式**：因為資料庫第一片還沒合併。這是刻意安排，不是閒置。
- **Dev-C 後半段同時負責後端（Phase 9、10）與大部分前端頁面**，容易被切碎（2026-11-16 起 Phase 9、10 後端已轉給 Dev-A，#18）。若進度落後，優先順序是先 12.1、12.9，再 Phase 9，最後 12.12、12.13。
- **QC 領先一個 Phase** 要求 QC 在 W1 就懂 spec 很細，QC 的前置準備量比一般更大；開工會前請 QC 先讀完 spec 第 3、4、7 章。
- **分線只依任務數與 AC 數粗略平衡，沒有工時依據**。做完 W1 後，依實際完成速度再調整分線。

與會：你、Dev-A／B／C、QC-1／QC-2。開會前請全員先讀 spec.md 第 1、3、4、7 章與本檔第 0、1、5 節。

## 6. Vibe coding 作法與護欄

開發改用 vibe coding（開發者以 AI 協助生成程式碼）。這會改變風險所在：程式碼產出變快，但「AI 悄悄改動不該改的東西」與「AI 連測試一起改弱」變成主要風險。以下規則補在第 5 節之上。

### 6.1 讓 AI 產出可控的輸入

1. **spec.md 是每次提示的固定上下文。** 每個任務的提示都附：對應的 `FR-*`、`AC-*` 條文、該 Phase 的「對外契約」、相關 DDL 片段。不憑記憶或口述。
2. **一個任務編號 = 一個提示單元。** 任務（例如 3.4）直接當作提示的範圍；一次提示不跨多個任務，避免 AI 順手「改良」別處。
3. **先寫測試再生成實作。** 提示順序：QC 的 AC 驗收測試（已存在）→ 請 AI 讓它轉綠。不先生成實作再補測試。
4. **spec 衝突不讓 AI 自己選。** 提示中明寫：遇到 spec 不明或衝突，停止並回報，不自行決定。

### 6.2 保護不可被 AI 改動的東西

| 保護對象 | 做法 |
| --- | --- |
| QC 的驗收測試與夾具庫 | 放獨立目錄，以 CODEOWNERS 指定 QC 才能改；開發的 PR 若動到該目錄，CI 失敗 |
| DDL 與遷移 | 同上，只有 Dev-A 的 PR 能動；CI 檢查既有遷移檔未被修改 |
| 凍結的函式簽名（`write_event`、`adjust_due`、`AIClient`）| 加簽名測試：用反射檢查參數名稱與順序，變動即紅 |
| 錯誤碼清單 | 單一檔案，測試比對 spec 5.2 的完整清單 |
| FR-AI-06 防回歸測試（3.5、7.9、9.4、12.2）| 標記為受保護測試，刪除或放寬需你核可 |

### 6.3 審查要看什麼（因為程式不是人逐行寫的）

1. **看 diff 的範圍，不只看功能對不對**：有沒有動到任務以外的檔案。PR 描述須列出「改了哪些檔、為什麼」，AI 生成的描述也要核對 diff。
2. **看有沒有繞過規則**：例如直接寫 `events` 而不經 `write_event`、直接 UPDATE `orig_due`、在候選確認時預填 `reason`。這些是 AI 最容易走的捷徑。
3. **看測試是否真的在測行為**：AI 容易寫出永遠通過的測試（斷言空洞、mock 掉被測對象）。開發自己的單元測試也由審查者抽查。
4. **依賴新增要審**：AI 常順手加套件；新增依賴須在 PR 說明理由。

### 6.4 QC 在 vibe coding 下的重點

1. **變異驗證**：對關鍵規則（如 `MARK_REQUIRED`、`orig_due` 不被改期覆寫、事件不可變）人工做「故意改壞實作，確認測試會紅」，確認驗收測試不是空的。
2. **探索式測試占比提高**：AI 生成的程式在規格沒寫到的邊界（極端日期、空字串、重複提交）較易出錯，QC 每個 Phase 驗收時保留固定時間做邊界探索。
3. **回歸套件每次 PR 全跑**：AI 修改易有連帶影響，不只跑本 Phase。

### 6.5 對本計畫的調整

- 第 5.6 波次表不變，但**「生成」不再是瓶頸，瓶頸變成審查與驗收**。QC 領先一個 Phase 的規則因此更重要，不可省。
- 小而頻繁的 PR 優於大 PR：AI 一次能產出很多，但審查者一次只能看得清有限的 diff。建議單一 PR 限制在一個任務群組內。
- 契約凍結（5.7）與保護清單（6.2）在開工會一併簽核。
